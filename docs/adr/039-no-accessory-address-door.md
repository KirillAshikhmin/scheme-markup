# 039. Двери адреса аксессуара сняты: адрес читается из номера метки

Статус: принято · 2026-11-08 · дополнено ADR 041 (адрес в опциях привязки
узнаётся **по форме** `aid[.sid[.cid]]`, а не по имени поля; ссылок по
идентификатору в опциях не бывает, и дом обходит привязку на один уровень)

Дополняет ADR 012 (адрес из `mark.id`), ADR 034 (адрес — номер метки) и ADR 035
(номер — десятичная строка).

## Контекст

После ADR 034 `deviceAid(markId)` стал двумя строками — «номер метки числом», —
а `deviceAids(project)` — картой `Map<markId, aid>`, в которой ключ и значение
повторяли друг друга. Заказчик:

> Он же не нужен теперь можно использовать идентификатор

и на прямой вопрос о судьбе дверей — «убирай». Требование G392.

## Решение

Двери `deviceAid` и `deviceAids` сняты из `src/sim/home.js`. Адрес аксессуара
читается на месте: `model.idNumberOf(mark.id)`. Поиск «метка по адресу» стал
поиском метки по её id (`findMark`) — карта для этого больше не нужна.

**Правило осталось в силе и переехало в `idNumberOf`:** id, который не
десятичная строка (uuid прежней разметки, встроенный ключ справочника, мусор),
адреса не имеет, и аксессуара у такой метки нет. Поэтому `idNumberOf` **больше
не принимает число**: прежде оно отвечало `idNumberOf(17) === 17`, а строгость
«только строка» держала дверь `deviceAid`. Теперь строгость одна и живёт в одном
месте.

Слово «адрес» из продукта не ушло: `aid` совпал с номером метки, а `sid` и `cid`
по-прежнему адресация хаба (нумерация с 13 внутри аксессуара). Журнал, разбор
адреса в сценарии и окно «Аксессуар» работают как работали.

## Почему

- **Голый `Number(mark.id)` по месту** — отвергнуто: он принял бы `17` там, где
  идентификатором считается только `"17"` (ADR 035), и два аксессуара одного
  адреса хаб молча потерял бы (`byAid` в `hubApi`). Дверь к числу в сборке одна —
  `idNumberOf`, — и своего `Number(id)` рядом с ней заводить нельзя.
- **Оставить `deviceAids` ради трёх её читателей** — отвергнуто замером: каждый
  зов снялся одной строкой. `deviceMigrate` спрашивает адрес одной ведущей метки
  (`idNumberOf(lead)`), окно «Аксессуар» — одной показанной
  (`idNumberOf(mark.id)`), а подсказка в сценарии искала метку по адресу — то
  есть по её же номеру, и теперь просто спрашивает `findMark`. Переписанного
  цикла не вышло ни в одном из трёх: три копии одного обхода вместо одной двери
  были бы не упрощением, и заказчик такого не просил.
- **Ослабить `idNumberOf` до «строка или число»** — отвергнуто: тогда правило
  снова оказалось бы в двух местах, и место номер два пришлось бы искать по
  исходникам. Число в чужом JSON (руками собранный файл) теперь не принимается
  как id и отправляет объект на перенумерацию — там он и получит честную
  десятичную строку.

## Последствия

- Имён `deviceAid` / `deviceAids` в сборке нет; `src/sim/home.js` держит на их
  месте надгробный абзац с доводом — иначе следующий завёл бы их заново.
- `idNumberOf(17)` отвечает `null`. Объект с числовыми `id` (в сборке такого не
  бывает, руками собрать можно) считается непронумерованным и перенумеровывается
  целиком — это верный ответ, а не потеря: номер по ADR 035 — строка.
- Тесты, стоявшие на дверях, проверяют то же правило через `idNumberOf` и дом;
  ни один не проверял только существование двери, поэтому удалять не пришлось
  ничего. Сверка «метка без номера в карту адресов не попала» заменена на «метка
  без номера не попала в дом аксессуаром» — так она говорит о правиле, а не о
  структуре данных.
