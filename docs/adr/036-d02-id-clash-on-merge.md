# 036. D02: у разошедшихся копий счётчик один, столкновение номеров разводит слияние

Статус: принято · 2026-11-08 · дополнено ADR 038 (столкновение ищется **внутри
вида**: номер свой у каждого вида, и метка 110 рядом со стеной 110 —
обычное состояние объекта, а не спор)

## Контекст

План исходил из уникальности номеров. Код показал: у двух разошедшихся копий
объекта счётчик общий по происхождению, и обе могли выдать новой метке один и
тот же номер.

## Решение

При слиянии столкновение разводит `mergeIdClash`: сторона, чей номер
переезжает, выбирается симметрично (результат не зависит от порядка
аргументов), ссылки на неё переписываются, отчёт сообщает `reissued`. Полностью
столкновение снял бы только номер, уникальный между участниками, — это
продуктовое решение владельца, пока не принято.

## Почему

- **Номер с меткой участника (17-а / 17-б)** — отвергнуто: ломает решение
  «адрес аксессуара = номер метки» (ADR 034) и возвращает длинные идентификаторы.
- **Отказать в слиянии и назвать причину** — рассматривалось и проиграло:
  разведение номеров дешевле для человека («вернуть лишнюю метку — минута,
  восстановить потерянную некому»).
- **Выбирать переезжающую сторону по порядку аргументов** — отвергнуто: слияние
  A+B и B+A давали бы разные объекты.

## Последствия

- После слияния метка может сменить номер, а с ним адрес аксессуара: привязки
  логики переедут, адреса в текстах сценариев нет.
- Сменившийся номер заметен в отчёте, но не в самом объекте; сценарий, где адрес
  вписан числом, молча укажет на чужую метку, если новый номер совпал с
  вписанным.
- Окончательно вопрос закроет только уникальность между участниками.
