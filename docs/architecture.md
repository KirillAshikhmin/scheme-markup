# Архитектура «Разметки схем»

Карта для того, кто правит код, — в первую очередь для агента. Отвечает на «где это живёт, через что течёт и что нельзя ломать». Не повторяет:

- **что умеет сервис и как достать данные из объекта** — `AGENTS.md` (рядом);
- **правила и ловушки сборки** — раздел `scheme_image/` корневого `AGENTS.md` («Правила, которые нельзя нарушить», «Ловушки»);
- **почему решения такие** — `docs/adr/001…022`;
- **слова предметной области** — `CONTEXT.md`;
- **точные сигнатуры и доводы** — шапки самих модулей. При расхождении прав код, этот файл чинят.

Числа (строки, тесты, миллисекунды) — на 2026-11-08; они стареют, структура — нет.

## 2. Целиком

Одна статическая страница: ни сервера, ни зависимостей (ADR 001), ни сети. Объект живёт в IndexedDB браузера, переносится zip-файлом.

```
src/**/*.js + src/**/*.css + src/index.html
        │  node build.js  (своя склейка: топосортировка импортов → один IIFE)
        ▼
dist/index.html  ≈3,0 МБ  ── страница целиком: код и стили без комментариев, строки
   └─ внутри строкой SIM_WORKER_SOURCE — второй бандл (поток имитации, ADR 010), ≈323 КБ
dist/assets/gost-type-a.ttf, sw.js, manifest.webmanifest, значки, guide.html
        │  git subtree split --prefix=scheme_image → KirillAshikhmin/scheme-markup
        ▼
GitHub Actions: npm test → npm run build → GitHub Pages
               + отдельно: свежая сборка = dist/ в git (работа dist)
```

`dist/` лежит в git и собирается байт в байт. Правка `src/` без пересборки `dist/` — недоделанная правка.

## 4. Состояние и поток правки

```
project (один объект JSON, ссылкой)          getState() — снимок: filter, view, выделение — копии
   │ функция model.js → НОВЫЙ project        (исходный не меняется никогда)
   ▼
canvasCommit(before, after, label, opts)     canvas.js — единственное место pushCommand (history.js, глубина 100)
   ▼
setState({project, …})                        app.js → подписчики subscribe(), simSync(project)
   ├─ панели перерисовываются (scheduleFrame — кадр без rAF-гонок)
   ├─ store.js: автосохранение документа в IndexedDB (`projects`, `images`, `settings`)
   └─ имитация пересобирает дом (§7)
```

- **Мутатор объекта — только `model.js`.** Каждая функция возвращает новый объект: `{project, …}` или значение.
- **Отменяемое — только через `canvasCommit`.** Единственное исключение — удаление схемы: картинка уходит из IndexedDB безвозвратно, причина в абзаце над `removeScheme`.
- **Экран, а не объект:** выделение, фильтры, скрытые вещи, слои, вид «Объёма», выбор погоды, состояние имитации живут в состоянии сеанса и настройках браузера (`store.js`), в `project.json` не попадают.
- **Файл:** `projectFile.js` — свой zip (`writeZip`/`readZip`) с `project.json`, планами и README. Загруженный объект проходит `autosave.adoptLoadedProject` (новые id), затем миграции. Слияние двух экземпляров — `merge.js`.
- **Ссылка:** `viewLink.js` — второй способ передать объект: чистка, короткие id, brotli, base64url в адрес после `#`; таблиц оригиналов и адресов хаба в нагрузке больше нет — идентификатор сущности сам короткий номер, а адрес аксессуара читается из него (ADR 030, 039). Счётчики видов в нагрузке есть, поэтому объект, пришедший ссылкой, перенумерован не будет (ADR 038). Формат обратим (`viewLinkRead(viewLinkPack(p)) === viewLinkStrip(p)`), кодек приходит аргументом — ADR 021 (формат), ADR 030 (номера вместо uuid) и ADR 022 (brotli копией в `web/vendor/`).
- **Связь метки с вещью, номера, формат 9** (ADR 030–039; договор — `.autopilot/2026-11-06-mark-object-link--wip/interfaces.md` и раздел «Таск 251» в `.autopilot/scheme-markup/interfaces.md`):
  - `mark.objectId` — единственное поле связи (`markObjectId`, `markObjectCan`, `setMarkObject`, `markOfObject` в `model.js`); обратной ссылки в файле нет. Место, габарит, угол и высоту связанной метки отдаёт **только** `markPlace(project, mark)` (`from: "object"|"mark"`); `mark.points` не переписывается, посты блока к связанной метке не применяются.
  - **Кто держит место знака на плане — одна дверь** `markPlaceHolder(project, mark)` → `{object, points, atMm}` (ADR 040, таск 252), собранная целиком из `markPlace`. Её спрашивают все четверо: кадр и клик (`render.visibleMark`), рука (`moveMarkPlace`), автопривязка к стене (`markPointsMm` → `applyMarkWalls`) и к помещению (`applyRoomOutlines`). Правило одно — **едет тот, чьё место знак держит**: у связанной точечной метки на калиброванной схеме это вещь, у всех прочих (нет связи, нет моста мм ↔ доли, линия, блок многих точек) — точки самой метки. **Край плана держит знак** и у вещи тоже (`planFitShiftMm`, `planBoxMm`): зажим стоит у жеста плана, а не в `moveSchemeObject` — «Чертёж» подложкой не ограничен. **Попадание ровно на ось стены — ничья, а не «стороны нет»** (`wallTieSide`: помещение метки → единственная сторона с помещением → «слева»): прежний `null` уносил прибор с обеих развёрток разом.
  - Вещь-устройство: `objectDeviceMake(project, objectId, typeId)` / `objectDeviceDrop`; носитель электрики — метка, у вещи своих номера и типа нет.
  - Идентификаторы сущностей — десятичные строки, и **счётчик свой у каждого вида** (ADR 038): ключ `counters["#" + коллекция]` (`idCounterKey`, перечень видов — `ID_OWNER_KEYS`; выдача — `nextId(project, вид)` / `nextIds(project, вид, сколько)`). На любом объекте первая метка — №1; номер 5 — это и метка, и помещение, и это нормальное состояние. Общий счётчик `"#id"` — надгробие `ID_COUNTER_SHARED_KEY`: по нему узнаётся объект формата 8. uuid остались у `project.id`, `project.key`, `scheme.imageId`, узлов дерева блочного сценария.
  - **Вид числа назван, а не угадан**, и это держит весь формат. Названия живут в трёх таблицах `model.js` и больше нигде: `ID_OWNERS` (поле ссылки → коллекция), `idsRewrite` (ссылки непростой формы — `mark.controls`, `device.doorId`, дерево блоков сценария, адреса в опциях привязок), `ID_KEY_SUBJECTS` (ключи принятых предупреждений: код проблемы → вид каждого сегмента ключа; код, которого в таблице нет, не переписывается вовсе). `idsReplace(project, {вид: {было: стало}})` принимает замены только названными по видам. Единственное место, где число приезжает без поля, которое назвало бы вид, — **значения опций привязки и текст сценария хаба**: там его опознают по форме адреса `aid.sid[.cid]`.
  - Адрес аксессуара — номер метки, и **своей двери у него нет** (ADR 039, G392): `idNumberOf(mark.id)` по месту, поиск «метка по адресу» — `findMark`. `idNumberOf` принимает только десятичную строку. Рецепт адреса поры uuid — надгробие `idsLegacyAid`; рецепт адреса под общим счётчиком — прежний номер метки (`idsAidMoves`), им адреса в опциях привязок переселяются второй раз.
  - **Ссылки по идентификатору в `logicBinding.options` не бывает** (таск 275): там значения опций самого скрипта (`info.options`), а единственное ссылающееся значение — адрес аксессуара, и узнаётся он **по форме**, а не по имени поля. Поэтому глубоко по значению обходится только **дерево блоков сценария** — и перенумерацией (`idsMovedTree`), и домом (`sim/home.js: homeLeadMarks`), — а привязку дом обходит на один уровень (`homeLeadBindings`): опцию, которую автор скрипта назвал `markId`, он не трогает.
  - **Номер, принятый снаружи, идёт через счётчик** (`idMint.claim`, единственная такая дверь — `addScenario`): занятый номер прикрывает выдачу лишь пока сущность жива, а отставший счётчик выдал бы её номер после удаления — и ссылка в никуда ожила бы чужой сущностью (та же порча, из-за которой есть `ID_GONE`).
  - Перечень ссылок для тестов — `ID_OWNER_REFS` (снят с `ID_OWNERS`): проверка «каждый номер переехал на ту же сущность» стоит на фикстуре, где заполнена **каждая** ссылка, а номера в ней разведены по видам, чтобы обход шёл по значению и таблиц модели не знал.
  - Версия файла 9 (`FORMAT_VERSION_KIND_IDS`, `projectFormatVersion`; признак — счётчики видов в объекте, `idsNumberedByKind`). Три входа в перенумерацию: uuid (формат ≤ 7) → по видам; формат 8 с общим счётчиком → по видам, адреса переезжают второй раз; уже по видам → **тот же** объект по ссылке. Вещи для меток ТВ/ПОС/ВЫТ достраивает `deviceMigrate.migrateThingMarks`. Без калибровки схемы метка в вещь не переводится.
  - **Ссылка в никуда гасится, а не остаётся числом** (ремонт таска 251): при полной перенумерации неизвестное число становится `ID_GONE` (`"0"` — ноль идентификатором не бывает), и проверки «жива ли ссылка» говорят то же, что говорили; неизвестный uuid проходит насквозь. Полноту таблиц объявляет вызывающий (`idsRewrite(..., whole)`): `idsMigrate` — да, `idsReplace` — нет. Адрес в опциях гасится только у объекта с пронумерованными метками.
  - Обозначение: `labelOf(project, markId)` — метка, `blockLabelOf(project, groupId)` — блок. Одной двери «метка или блок» больше нет: метка 1 и группа 1 живут в объекте одновременно.
  - Предел тел модели: вещь 15 (`OBJECT_MODEL_THING_BODY_MAX`), метка тоже 15 (`OBJECT_MODEL_BODY_MAX`, поднято в таске 260 словом заказчика); разводят их теперь грани — вещи 90 (пятнадцать коробок), метке 100 (десять круглых тел), выбирает `objectModelLimits(key)`; в каталоге вещей 67 предметов, ТВ, полотенцесушитель и вытяжка — и вещь, и изображение метки; у робота-пылесоса (таск 261) ключи разные — `vacuum` у метки, `robotVacuum` у вещи, — а тело одно, ссылкой, как у щита (`panel` и `panelBox`); знак метки с таска 264 тоже смотрит сверху, круглым роботом.
- **Миграции (G68):** две трубы открытия — `projectFile.migrateProject` (файл) и `panels/projects.js: projectsMigrateStored` (база; её зовёт `openProjectById`); перевод аксессуаров — `deviceMigrate.js`. Новое поле получает выведенное значение. Тест — объект прежней версии (`test/legacy-*.json`, `test/fixtures/g68-legacy-*`) открывается без единого изменения.
- **Координаты:** точки меток — доли плана 0…1 (ADR 002), чертёж — целые миллиметры (ADR 008). Перевод — `planFractionToMm` / `planMmToFraction`; масштаб и начало у схемы задают `setPlanScale` / `setPlanOrigin`.

## 5. «Схема», «Чертёж», выгрузки

- **`render.js`** — чистое рисование по холсту-аргументу: `drawScheme` (метки, подписи, связи, живое состояние `live`/`liveFx`), `drawDrawing` (стены, проёмы, вещи), геометрия фигур и начертаний, `hitTest`. Без `live` `drawScheme` не делает ни одного лишнего вызова `ctx`: в тестах кадры сверяются журналом вызовов.
- **`canvas.js`** — поле «Схемы»: жесты (через `gestures.js` и `planNav.js`), режимы, постановка меток, блоки, ломаные, помещения контуром, `canvasCommit`.
- **Перенос знака — одна дверь модели** `moveMarkPlace` (таск 252, ADR 040): `canvasMoveMarks` зовёт её на каждую везомую метку одним вектором в долях, и каждая метка двигает того, чьё место держит её знак (`markPlaceHolder`) — связанная точечная на калиброванной схеме везёт **вещь**, прочие свои точки. Блок из этого складывается сам и уходит в историю одним шагом; ярлык у прибора свой — `history.moveDevice`. Притяжка к направляющим и выбор ближайшей вершины считаются по **видимому** знаку, а не по записанной точке. Своего списка «кого везти нельзя» у холста нет.
- **Порядок меток на экране — одна дверь** `render.visibleMarks` (таск 238): она отдаёт метки схемы снизу вверх, спросив порядок у модели (`marksInDrawOrder` по ярусу `mark.z`, умолчание 0 — верх). Через неё метки берут и кадр, и `hitTest`, и стопки, и раскладка подписей, и все выгрузки с мини-планом, поэтому клик всегда достаётся той метке, которую видно сверху. Правят ярус четыре команды в карточке метки через `canvas.canvasMarkOrder` → `model.moveMarkOrder` → `canvasCommit`; те же четыре зовутся с клавиатуры (`canvasOrderKey`: `]` и `[`, с Shift — на передний и задний план, таск 240) и при тех же условиях, по которым гаснет кнопка. **Место в массиве `project.marks` ярусом не трогается** — его читают как «порядок постановки» `marksInRoomOrder` (смыкание номеров), `marksInOrder` (перечень «чем управляет») и `deviceFollowers` (ведущая метка устройства). **У метки из блока команды расходятся по тому же шву, по которому они уже расходились на фильтре** (таск 262, G385, `canvas.canvasOrderSolo`): шаг «выше»/«ниже» двигает её **одну** и шагает через соседа по блоку (`canvasOrderAmong` сужает `among` до «видимое ∩ блок»), а «на передний план»/«на задний план» везут **весь блок**, как и перетаскивание (G189). Второй клавиши для этого не завелось; оба случая названы в подсказке кнопки (`strings.markCard.order.block` и `blockStep`).
- **Сетка блока — полшага знака** (таск 262, G380): метку, которую ведут **одну внутри блока** (Ctrl/Cmd у мыши), холст кладёт в узел сетки — `canvas.canvasBlockSnap` → `model.blockGridSnap`, шаг `blockGridPx` = половина `blockStepPx`, то есть своего числа у сетки нет и ползунок величины меток двигает её вместе с собой. Начало отсчёта — знак **первой метки блока** (`group.markIds[0]`, её место даёт `markPlaceHolder`): сетка привязана к блоку, а не к листу, и всё, что поставила ручка «+» (целый шаг = две клетки), стоит в узлах само. Блок, который везут целиком, едет свободно и везёт сетку с собой; одиночную метку ловить не за что. Alt снимает сетку тем же движением, каким снимает направляющие, — вторая клавиша «без магнита» не заводится, а порядок притяжек назван: сперва сетка, потом направляющая (проведённую рукой линию сетка не перебивает).
- **Блок из готовых меток — одна дверь** `canvas.canvasStartBlockJoin` (таск 244): шестой режим холста (`CANVAS_MODE_BLOCK_JOIN`), устроенный как калибровка и помещение по чертежу — подсказка над планом, плашка о входе, крестик вместо курсора, Esc на выход (`canvasStopBlockJoin`, одна дверь на Esc, кнопку и уведённое выделение). Отличие одно: выделение не снимается — первая метка блока берётся из него, а ручки гаснут (`canvasHandlesShown`), иначе «+» отобрал бы клик у соседа. Правит объект модель: `joinToBlock` (хозяин — блок показанной метки) и `leaveBlock` (группа меньше двух меток распускается, как при `deleteMark`); **ни одна точка не двигается и порядок массива `project.marks` не трогается**. Кнопки — ряд «Блок» в `panels/markCard.js`, рядом с рядом «Порядок».
- **`panels/workshop.js`** — «Чертёж» поверх того же поля: стены (`splitWall`), проёмы из `openingCatalog.js`, вещи из `objectCatalog.js` (`turnDeg`, «К стене»), развёртка (`panels/elevation.js`).
- **Высоту вещи на развёртке называет посадка, а не ключ файла** (таск 264, G405): `wallElevation` кладёт в `sizeMm.height` поле `sizes[axisUpField(seat)]`, где посадку даёт та же дверь `axisSeatOf`, какой её спрашивает карточка. Второго ответа на «какое поле вверх» в сборке нет. Метка без высоты силуэта не получает вовсе — она уходит знаком в полосу под полом, — поэтому лист готового объекта правка не двигает ни на штрих.
- **Подпись метки на развёртке не шире, чем до соседа** (таск 273, `render.elevationLabelRooms` + `render.elevationLabelFit`). Подпись связанного прибора — пара «ТВ1 · Телевизор» плюс высота, и на плотной стене она налезала на соседнюю. Запас считается **разом** на все подписи меток листа (ряды, линейные метки, полоса под полом — своим списком) как расстояние до ближайшего соседа: если каждая подпись не шире промежутка, их половины его не перекрывают, то есть наезда не бывает. Не влезло — подпись **сдаёт части в названном порядке**: сперва имя вещи (её изображение и так на листе, а имя — в списке стены и в таблице), потом высоту над полом; **обозначение остаётся всегда** — по нему прибор находят в таблице. Имя вещи снимается тем же шаблоном `markObject.pairLabel`, которым модель его приклеила. Второй раскладки подписей у развёртки нет, и мерки холста (`measureText`) у неё своей тоже нет — меряет тот же `ctx` тем же шрифтом, которым рисует.
- **Поля вне «Схемы»** (мини-план «Сценариев», схема в окне) — `panels/planView.js` тем же `drawScheme` и тем же `planNav`. Второго механизма хода по плану нет.
- **Выгрузки:** `exporter.js` (PNG схемы и таблиц, zip всех схем, печать) рисует тем же `drawScheme` с `zoom = scale`; `gostSheet.js` — лист ГОСТ с рамкой и штампом; `mono.js` — ч/б; `pdf.js` — свой PDF растровой страницей (ADR 007); `pngDpi.js` — физический размер в PNG; `tables.js` — CSV, Markdown, TSV.
- **`tools/scheme.mjs`** — те же выгрузки из командной строки без своего счёта: импортирует модули страницы. Браузерные команды (`plan-png`, `volume-png`) поднимают свой Chrome мостом `tools/schemeSheets.mjs`.

### 6.3 Решения, на которых всё стоит

- **Свой рисовальщик по Canvas 2D, не WebGL** (шапка `volume.js` — двери модулей): одна среда рисования с планом и развёрткой, без библиотек. Узкое место — заливка пикселей, а не арифметика.
- **Порядок граней — дерево разбиения (BSP), не сортировка** (D32, D33): строится при сборке сцены, обходится за `n` на кадр, верен в каждом пикселе. Поэтому прозрачным вещам второй проход не нужен. Ярусы `VOLUME_LAYER_*` (плита, тень дома, полы, солнечные пятна, тела) кладутся до и после дерева.
- **Время суток — одно непрерывное число** (высота солнца), а не четыре состояния: ни одного «если ночь» в рисовании.
- **Физический свет** (отметка «Физический свет», по умолчанию включена):
  - лампа кладёт пятно кольцами на грани своей комнаты и клином сквозь открытый проём к соседке;
  - окна днём светят комнату (`skyDecals`);
  - вещи каталога бросают тень от ламп своей комнаты (`occluders`). Тень снимает только свет своей лампы (`volumeShadeAlpha`);
  - без отметки свет комнаты заливает её целиком (`volumeRoomTint`).
- **Помещение светлит источник, а не метка** (таск 248, G375). Помещение лампы заводится **в одном месте** — `volumeLampSources(place, scene, roomId)`: каждый источник несёт `room`, и свет комнаты (`volumeLiveLight`), и пятна с тенями (`volumeLampDecalsBuild`) берут помещение у него. У точечной лампы источник один и правило прежнее: `roomId` метки старше пробы якоря (`volumeMarkProbe`). У ломаной (лента, трек) источник стоит на каждом метре (`volumeLampPieces`), и помещение спрашивает **каждый кусок** — лента по периметру потолка через два помещения светлит оба, а `roomId` метки отвечает только за метку (журнал, сценарии, «чем управляет»). Делится при этом `volumeLampPower` целиком: доли кусков складываются в неё, и лента, лежащая в одном помещении, светлит его ровно как светлила. Кусок вне всякого помещения (лента вышла за контур) не светит ничего — прежде из-за него гасла вся лента. Пробы помнятся на место метки (`volumeLampRooms`, `WeakMap` по `place`): `volumeLiveLight` зовётся на каждый кадр, а проба на кусок вместо пробы на метку умножает счёт на число кусков.
- **Свет не обрывается на открытой границе** (таск 250, G378). Где свет проходит между двумя помещениями, знает **один список** — `volumeLampOpenings(scene)`; из него берут и клин лампы, и свет неба, и перелив. В нём границы двух видов: проём в стене (у солнца, `scene.sunSpots`: проём без полотна, открытая дверь, открытая створка, стеклянная стена во всю стену) и **граница без стены** (`volumeRoomBorders`) — две кромки контуров лежат встык, а стены между ними нет вовсе (студия, гостиная с кухней: зона на помещение). Дыра двусвета в список не нужна — в стопке она уже носит ключ помещения под собой (`volumeStackRoomAlias`). Через такую границу идёт то же, что сквозь проём: **клин пятна** (`volumeSourcePools`; косяков у границы нет, поэтому точка одна вместо шести, а перемычка срезана — `volumeOpenTop`) и **перелив** (`volumeLampSpill`): светлота соседки подтягивается к светлоте помещения на долю открытости, `площадь / VOLUME_LAMP_OPEN_MM2`. У двери 900 × 2100 это прежние 0,3, у границы без стены и у стеклянной стены — единица, и тогда светлота у двух помещений одна: перепада нет вовсе. Перелив **подтягивает, а не прибавляет** — светлее соседки помещение не становится, и светлой полосы на границе не возникает. Закрытая дверь в список не попадает, и перепад у неё прежний. Без отметки «Физический свет» проём в стене свет не выпускает (так эта отметка и задумана), а граница без стены — выпускает: держать его там нечему.
- **Свет считается лампа за лампой, и только у горящих** (таск 253, G389). Единица пересчёта — **лампа**: её кольца и тени ни от какой другой не зависят (`volumeSourcePools` кладёт их на куски её помещения и клином через открытые границы — ровно на один шаг), а помещение как единица было бы той же работой с лишним запасом. Единственная связь между лампами — смесь теней (`volumeShadeMix`), и она живёт **на куске грани**: пересчитываются только куски, которых новая лампа коснулась. Строится геометрия **только у горящих** (`volumeLitLamps`): у погашенной лампы сила в `live.lamps` ноль, её кольца дают `alpha` ноль и в кадр не идут, а её доли в `mix` и `gone` тени множатся на ноль (`volumeShadeAlpha`) — поэтому кадр от «построено только горящее» совпадает с кадром от «построено всё» вызов в вызов. Построенное **не выбрасывается**: погасшая лампа свои кольца сохраняет, и второй щелчок по ней не стоит ничего; новая лампа вставляется в карты **по номеру** (`volumeMergeByMark`), на то место, где она стояла бы при полной сборке, — порядок колец на куске это порядок рисования. Цена: на самой большой схеме заказчика (177 ламп) первый щелчок по лампе 857 → 27 мс, следующий 3 мс; «зажечь всё разом» стоит столько же, сколько стоило (886 → 862 мс), а «зажечь все по одной» — дороже суммарно (1,0 → 1,5 с), потому что смесь теней куска пересчитывается на каждую новую лампу на нём. Светлота помещений (`rooms`, `volumeLampSpill`) считалась и считается заново на каждый вызов за 0,1 мс — делить её по частям нечего.
- **Картинка на лице прибора — грани сцены, а не тела** (таск 255, G394, G400). Экран телевизора и монитора и полотно картины несут имя картинки в описании тела (`art` в `objectModels/kit.js`), а фигуры и их цвета живут в `volume/art.js`: цвет тела принадлежит категории (ADR 005), а у неба и травы цвет свой. Телами картинку не нарисовать — на день таска 255 предел метки был пять тел, — поэтому это плоские грани на лице тела, по грани на фигуру (природа 7, окна монитора 5, геометрия картины 4). Лежат они в сцене рядом с гранями тела и получают там помещение, ярлык вещи и хозяина для щелчка, **но в дерево порядка не идут** (`volumeInTree`): плоскость в двух миллиметрах от лица стоила бы резов по всей сцене, а место в очереди им, как диодам, считается по середине. **Рамка — само тело вокруг стекла**, и мера у неё одна на телевизор и монитор и в миллиметрах (`VOLUME_ART_FRAME_MM` = 10): доля габарита дала бы 25 мм поперёк и 14 вдоль, то есть рамку разной толщины у двух приборов и неровную у каждого. Горит **стекло**, а не тело (`lit && !part.art` в `volumeModelFaces`), иначе светилось бы всё лицо и рамки не было бы видно; фигуры работающего экрана светятся своим цветом без тона часа (`led`, как диод и шкала), фигуры полотна не светятся вовсе — их освещает комната. Картинку экрана кадр рисует, **пока прибор горит** (`face.art === "screen"` в `volumeFrame`): выключенный экран — тёмное стекло в рамке, картина висит всегда.
- **У вещи-устройства тело одно — её собственное** (таск 255). Хозяин граней вещи — её метка (`volumeObjectFaces` → `markOfObject`), и ровно поэтому монитор компьютерного стола включается: живое состояние дома лежит по `markId`, а у граней вещи чертежа хозяина не было. Следствия: щелчок по вещи-устройству открывает её карточку, взгляд сквозь неё больше не проходит (правило `volumeSightAt` — «пропускается то, за чем всё равно никого не выделить»), а **связанная метка своего тела не рисует**, если вещь нарисована моделью (`volumeScene`): до этого телевизор, которому миграция достроила вещь, рисовался дважды, а на компьютерном столе вставал телевизор во весь его габарит. Вещь без модели рисуется габаритом и тело метке оставляет.
- **Пятна и тени без обводки.** Шов с соседним куском той же плоскости и той же комнаты закрывает раздача на полточки (`volumeSeamGrow`). Обычные грани обводятся своим цветом, иначе сглаживание проявило бы стыки BSP.
- **Режим только читает** (G68): ни одной записи в объект. Единственное, что уходит наружу, — выделение (состояние сеанса).
- **Краска стен, пола и потолка — цвет грани, а не второй слой** (правка 2026-10-25). Хранит её объект: `wall.paint = {left, right}` (стороны по ходу стены, как у развёртки) и `room.paint = {floor, ceiling}`, необязательные ключи, сброс удаляет ключ (`setWallPaint`, `setRoomPaint`, `setRoomWallsPaint` в `model.js`). Сцена кладёт краску в `face.rgb` (`volumePainted`): заливка, ночь, кольца ламп и пятна солнца берут цвет у грани сами. Узнавать стену, пол и потолок сравнением `face.rgb === VOLUME_WALL_RGB` больше нельзя — только `volumeIsWall` / `volumeIsFloor` / `volumeIsCeiling` (крашеная грань несёт `face.paint`). Пол в проёме — полосы под стеной по сторонам, откосы — половины по толщине: каждая берёт краску своей стороны. Изнанка двустороннего потолка — крыша, она держит цвет сборки (`face.backRgb`). Некрашеный объект собирается грань в грань прежним — кадры совпали байт в байт.
- **Дерево порядка помнит неподвижные грани** (правка 2026-10-27, фриз при открытии двери): `volumeOrderTree` строит дерево по граням без `doorId`, а полотна дверей, створки и ворота вставляет в него потом (`volumeOrderInsert`, копии узлов на пути — готовое дерево не меняется). Неподвижные грани новой сборки сверяются с прежними поле в поле (`volumeValueSame` — одна сверка на весь «Объём»): совпали — дерево берётся готовым (65 → 20 мс на дверь на объекте в 13 тыс. граней). Полотно двери — призма в 40 мм (`VOLUME_DOOR_LEAF_MM`), бруски створки — призмы глубиной рамы. **С таска 265 этажи стопки живут по тому же приёму**, только память у них своя — в ящике головного этажа пачки (`box.base`, `box.statics`, `box.baseCuts`), и живёт она ровно столько, сколько сцена (таск 232). Полная сборка пачки стала не нужна ни на дверь, ни на створку: на объекте заказчика с двусветом (17 тыс. граней двух продетых этажей) дверь стоила 98 мс, стала 30, а пересборка без правок — 7 вместо 98. Осталось два места, где дерево пачки строится заново: правка объекта и **первая смена этажа после открытой двери** (дерево стоит на прежних гранях пересобранного этажа — кадру этого хватает, а переезду нет, и сверка честно отказывается).
- **Ключ этажа сверяет метки по значению** (таск 265): список видимых меток приходит от `render.visibleMarks`, а та отдаёт связанной с вещью метке копию (`visibleMark`, таск 252) — сверка по ссылке не сходилась **никогда**, и кэш этажей таска 232 был мёртв на любом настоящем объекте. Отсюда же числа выше: до правки каждая сборка стопки стоила полной.
- **Стеклянная стена** (`wall.glass`, правка 2026-10-27) — те же грани стены, ставшие стеклом двери (`volumeGlassed`): кадр смешивает по `alpha`, взгляд смотрит сквозь по `clear`. Пятнам ламп она не стена (`volumeIsWall` по цвету), тени дома не бросает, человека держит. Для света она — проём во всю стену, разрезанный по помещениям (`volumeLightOpenings` в `volumeSunOpenings` и `volumeRoomLight`): солнце, луна, небо и клин лампы к соседке берут проёмы из `scene.sunSpots` и проходят сквозь неё сами.
- **Двусвет — одно помещение для света** (правка 2026-10-27): в стопке дыра этажа выше (помещение без пола) получает ключ помещения под ней (`volumeStackRoomAlias`), а низ и торец перекрытия этажа выше — помещения этажа ниже под ними; свой ключ грань хранит в `roomOwn`, связь пересчитывается на каждой сборке, в том числе у кусков дерева порядка. У стены над дырой полоса пола без напуска и без торца со стороны дыры. Падение в дыру — только когда «Объём» на экране (`fallFloor`), зато **при любом числе показанных этажей** (таск 265): падать можно только туда, что нарисовано, поэтому при одном показанном этаже стопка поднимается на время полёта (`fallShown` в `panels/volume.js`, второй повод у `stacking`) и снимается в миг приземления. Отметка «Все этажи» этим не трогается, переезд делает тот же `fallTo`, а «падать некуда» осталось одной причиной — ниже нижнего этажа земля (`strings.volume.fallNoBelow`).
- **Лестница собирается по габариту** (`objectModels/stairs.js`): плоские ступени по подъёму 175 мм, на пятую часть уже хода; Г-, П-образная и спиральная отражаются (`schemeObject.mirror`). Предел модели к ним не относится — лестниц на объекте одна-две; у остальных он разделён (`objectModelLimits`): тел по пятнадцать и тем и другим, а граней вещи 90, метке 100. Окно «на какой этаж» — с 400 мм и только из помещения лестницы (`volumeStairNear` со сценой).
- **Двери и створки окон — одно множество открытого** (`openDoors` в `panels/volume.js`, `openDoorIds` сцены): окна, кроме витража в пол (`openingVents`), открываются створкой — первой секцией лица, у балконного над поясом (`openingVentCell`, `volumeWindowSash`). «Все двери» (`R`) окон не трогает. Дом узнаёт о створке тем же `simDoor`: климат проветривает комнату площадью створки, датчик открытия в проёме окна ходит с ним (`markDoorOf`).
- **Блок стоит рамкой, а план от этого не двигается** (таск 239, G360): места постов считает `volumeBlockSeats` **раз на сборку сцены**, межцентровое — `VOLUME_BLOCK_STEP_MM` = 71. **Старшинство названо словами** (таск 263, G379, G381): высоту, которую назвал человек — свою или соседа по блоку (G203), — раскладка не трогает, и рамку собирает она; высота, о которой человек не говорил (умолчание типа или пустота), рисунку не спорит. Чьё это число, отвечает **одна дверь** `sizesHeightSaid` в `model.js` (рядом с `markSizes` и `sizesSaidNothing`, по той же причине — второго ответа быть не должно); само число не подменяется ничем, меняется только место (G68). Дальше раскладку решают **высоты и рисунок плана** (таск 242, G363): посты одной высоты — одна рамка, рамки разных высот встают друг над другом по середине блока; рядов у рамки столько, сколько их нарисовано на плане **в глубину комнаты** (`volumeBlockFrameRows`, граница ряда — полпоста, 35,5 мм), и **ближний к стене ряд — верхний** (таск 245, G368: «Ближе к стене — выше»; до него было наоборот). Ряд рамки получает свою высоту (`seat.heightMm`), заданная остаётся серединой. **Колонок у рамки столько, сколько их нарисовано вдоль стены** (таск 246, G371, `volumeBlockColumns`, та же мера в полпоста): место поста — номер его колонки, а не номер в своём ряду, поэтому ряд покороче начинается там, где он начат на плане, а не центрируется сам по себе. Пустых колонок не бывает (колонку заводит пост, а не расстояние), и в одной колонке не бывает двух постов одного ряда — этим и держится «однорядная рамка стоит, как стояла». **Лицо поста — до соседа** (таск 246, G372; по вертикали — таск 247, G374): посты делят одну накладку, а 80–86 мм это размер одиночной рамки, поэтому лицу достаётся столько, сколько есть до соседа в этом измерении (`seat.tightAlong` / `seat.tightUp` — миллиметры, а не отметки). Вдоль стены сосед — колонка через модуль (ответ таска 246 прежний до доли), по вертикали — ближайший **ярус блока**: у рядов одной рамки это снова модуль, у рамок разных высот — разница заданных чисел, и столбик, в котором высоты вписаны через 70 мм при лице 80, перестаёт налезать сам на себя. Мера симметрична (середина тела остаётся записанной высотой — по ней целится выделение и приходит связь) и общая на рамку, но **не** на блок: рамка с рядами меряется своим модулем, а одиночная рамка того же блока — своей далёкой соседкой. Заданные высоты под модуль не подгоняются, рамка из одного поста и одинокая метка габарита не теряют, записанный габарит не меняется нигде (G68). **Пост, о размерах которого не сказано ничего, рисуется модулем** (таск 247, G373): габарит у него догадан целиком (изображение объекта, а без него рамка 80), и в блоке подрозетников честная догадка — пост, а не силуэт вещи во всю стену («Кабель-канал» 400 × 500); названа хоть одна сторона — габарит остаётся его, у одинокой метки запасной габарит цел (G226, G230), а строка под полем о догадке называет и модуль (`markSpare.js`, поле `postMm` в `volumeMarks().spare`). Рамка, нарисованная одной линией в глубину (в каждом ряду по одному посту), остаётся одним рядом вдоль стены — но **только при заданной высоте** (таск 263, G379): её число с места не сдвигается. Высоту из справочника держать нечем, и такая рамка встаёт как нарисована: две розетки одна за другой в глубину — вертикальная пара, блок шахматом — шахматом (G380, хвост таска 262; до таска 263 шахмат собирался в один ряд). Направление (`volumeBlockAlongWall`) у рамки не спрашивается вовсе: ряды и колонки — уже две меры рисунка, и спроси вдобавок направление, шахмат потерял бы свои ряды. **Исключение**: блок, где на каждой высоте по одному посту, рамок не образует, и его расставляет направление относительно оси стены (таск 241, G361, `volumeBlockAlongWall`): вдоль — ряд лесенкой, поперёк или поровну — столбик. Порога в миллиметрах у направления нет: мерятся два разброса между собой. Отсчёт — от середины блока, порядок в ряду — порядок на плане вдоль стены, стена со стороной режет блок на рамки (угол). **Высота, которой нет, бывает двух видов** (таск 245, G369): у потолочной вещи её не бывает (габарит назван, посадка — нет), и в рамку такая не идёт; у вещи, о которой не сказано ничего (`sizesSaidNothing`, то же место решает посадку типа), высота просто не задана — такой пост встаёт в рамку и берёт у блока **самую низкую** из заданных высот, тем же правилом, что `markSizes` берёт высоту группы (G203). Делиться нечем — блок стоит, как стоял. Шаг знака на плане (`BLOCK_STEP_RATIO`, G182) не трогается: план — схема, и расхождение с объёмом здесь нарочное. Отсюда же второе: **у метки в объёме тело на каждую нарисованную точку** (`volumeMarkBodies`) — у поста рамки место считает блок, у остальных это сама точка, «где нарисовали, там и отображается» (таск 263, G382: четыре спота одной меткой стоят по своим точкам, а не одним телом посередине; прежде так стояла любая потолочная метка со многими точками). Исключение одно: связанный прибор стоит на месте вещи, и тел у него одно. `markId` у всех тел один, `volumeMarkPlace` по-прежнему отдаёт первое — выделение, щелчок, связи и прицел спрашивают метку, — а **свет раздаётся по всем телам**, поровну делённой силой метки (`volumeMarkPlaces` → `volumeLampSources`, тем же приёмом, которым лента светит каждым куском).

Стенд — `npm run bench` (счёт в Node) и `npm run bench:browser` (ещё и заливка в своём Chrome), сцены в `tools/bench/scenes.mjs`. Замер со сценой «квартира с мебелью» (`flat`), поле 844 × 390, после правки 2026-10-24:

- плотность холста ограничена двумя точками экрана на точку изображения (`volumeRatio`), а пальцем на ходу — одной (`volumeMotionRatio`): встал — через 160 мс кадр перерисовывается чётким;
- около 600 многоугольников на кадр;
- заливка около 6 мс на видеокарте Mac;
- JS-часть кадра около 0,5 мс;
- пересборка света **одной лампы** около 2 мс на обычной квартире и около 7 мс в комнате с 20 лампами и 48 вещами (столбики `1 лампа` и `+1 лампа` стенда); «зажечь все лампы разом» — прежние 10 и 128 мс (столбик `свет`). Она идёт разово: на смену ламп, двери или шторы.

Что дорого: число `fill()`, площадь холста, обводки. Новый эффект в кадре меряют прежде, чем принять.

На живом устройстве — адресом `?fps` (`src/fpsMeter.js`): в углу поля темп кадров, пока поле двигают, время счёта кадра в JS, грани и холст. Заливку видеокарты видно по темпу.

### 6.5 Окно и поверх-кадра

- `panels/volume.js` — кадр (`paint`), камера и стойка, клавиши (`E` — дверь или створка окна, `Q` — окно метки), сенсор (плавающий джойстик хода, взгляд свайпом), миникарта (`drawDrawing` через мост «пиксель = мм»), подписка на дом `simWatch`.
- **Щелчок равноценен `E`, и под захваченной мышью тоже** (G235, G376): куда целятся оба — `volumeAimAt` (курсор над полем, а под захватом середина поля), на что действуют — `volumeAimChoice` → `actOnChoice`. Чьё нажатие, холста или кнопки поверх него, решает `volumeFieldDown`: кнопки, карточка метки, площадка ходьбы и вопрос про этаж лежат своими узлами над холстом и полем не считаются, но **под захватом браузер адресует события мыши захваченному узлу** — стойке, а не холсту, и попадание в холст там не спрашивается (таск 249; до него щелчок под захватом не делал ничего). Порог сдвига, отличающий поворот головы от щелчка, под захватом не мерится нарочно: курсор стоит, двигается взгляд.
- **Прицел — узел разметки поверх холста** (`.volume__aim` в `panels/volume.css`), а не рисунок кадра: в снимок вида он не попадает. Белые штрихи в две точки со сплошной тёмной обводкой в точку (четыре `drop-shadow` без размытия) и разрывом посередине — читается и на белой стене, и на ночном небе; холст его не рисует и на бюджет кадра он не влияет.
- `panels/volumeParams.js` — окно параметров: фон, время, погода, слои, ходьба.
- `panels/volumeRain.js` — осадки своим холстом, маска дома — `volumeRainMask`.
- `panels/volumeAir.js` — окошко климата у часов.

Часы приложения — `src/appClock.js` (формулы в `src/clockMath.js`). Worker сам считает `clockSimMs(clock, Date.now())` и получает `setClock({simMs})`.

### Границы и соглашения

- **Живое состояние имитации не входит в объект.** Оно не идёт через `canvasCommit`, `setState({project})` или `project`, а живёт в зеркале `simulation.js` и в настройке браузера `simState` по ключу объекта (ADR 015). В объекте — только то, что задал человек: `type.device` / `mark.device` (профили), `project.scenarios`, `project.logicBindings`. Эти поля пишутся через `canvasCommit` со своим ярлыком `strings.history.*`.
- **Профиль выводится, а не пишется** (ADR 013): нет `type.device` — профиль считает `typeDeviceOf` по коду типа. Командам `setTypeDevice` / `setMarkDevice` передают только изменённые ключи; если ничего не изменилось, их не вызывают. Явное «без аксессуара» — `kind: "none"` (ADR 020).
- **Адреса не хранятся** (ADR 012, 034, 039): `aid` — это номер метки, `idNumberOf(mark.id)` по месту; своей двери у адреса нет. `sid` и `cid` считаются из профиля. Ключ устройства везде `mark.id`; обозначение метки не уникально. Метки одного типа с одним номером — одно устройство (`deviceFollowers`, `markDeviceLeader`).
- **Версия файла считается по содержимому** (ADR 014, `projectFormatVersion`): 7 — если хоть один сценарий стоит на ссылке в библиотеку (`scenario.lib = {name, version, hash}`), 6 — если есть сценарии или привязки, иначе 5. Текст сценария переводится на ссылку при открытии — **только при побайтовом совпадении** с библиотечным (`model.migrateScenarioLib`, обе трубы миграции, G24.1); поправленный своей рукой скрипт остаётся текстом в объекте, и запись хранит либо `source`, либо `lib`, но не оба. Реестр приезжает по сети, поэтому перевод идёт после открытия (`panels/projects.js: pinLibraryScripts`), а исходники дому подставляет `scenarioLib.js` до `buildHomeSpec`.
- **Чистые слои без DOM:** `sim/*`, `scenarioTree.js`, `appClock.js`, `clockMath.js`, `weather.js`. В бандл Worker не должны попадать DOM-модули — это проверяет `build.js: assertWorkerPure`. `model.js` не импортирует `sim/home.js`.
- **Worker** (ADR 009, 010) собирается вторым бандлом из `src/sim/worker.js` и кладётся строкой в `SIM_WORKER_SOURCE`. В исходнике строка пустая, текст подставляет `build.js`. Сторож в `bridge.js`: пульс раз в 1 с; если ответа нет 3 с, поток перезапускается, а виновный скрипт выключается. Новый поток получает `start {restore: true, memory}`: это продолжение, а не старт хаба — «на старте» и `onStart` не исполняются, а `GlobalVariables` возвращаются из памяти, которую поток после каждого события отдаёт странице сообщением `memory` (хук хозяина `memory()`). Первой строкой поток снимает сеть, хранилища и `navigator` и запирает код из строки (`simWorkerSeal`, `simWorkerNoStringCode`); `import(` в тексте сценария отвергает разбор (`hubScriptCompile`).
- **Хозяева сценариев** подключаются к движку списком `owners` в порядке `[hub, blocks]`. Хост-дверь (`host.*`) — единственное, что хозяин знает о движке. Новый вид сценария — это новый хозяин, а не ветка в `engine.js`.
- **Свой формат блоков** (ADR 011), не JSON Sprut.Hub. Файлы `.js` и JSON `scenarioTemplate` читает `hubScriptRead`; блочный JSON хаба получает отказ `hubBlocks`. Правила там, где вики молчит, — ADR 018.
- **Журнал — коды, а не тексты.** Движок пишет `code` + `vars`, текст получается как `text("sim.journal." + code, vars)`. Новый код заводится и в движке, и в `strings.sim.journal`.
- **Время имитации `simMs` — «местные мс»** (время на стенных часах, записанное как UTC). Читать его только через `getUTC*`.
- **Выключатель = реле + кнопка** (ADR 017, вид `switchRelay`). Один щелчок или нажатие обрабатывает `deviceCard.js` (`deviceClickPlan`, `devicePressers`) для всех трёх поверхностей.
- **Режим «Сценарии»:** `panels/scenarios.js` + `scenarioEditor.js` (блоки) + `scenarioScript.js` (JS). Они подключаются через `scenariosHook(...)` и друг друга не импортируют. Править можно только на десктопе.
- **`simSync(project)` на каждую смену `project`** (это делает `setState`). Правка объекта при идущей имитации пересобирает дом и сбрасывает ждущие таймеры (`editReset`).
- **Поток поднимается по надобности** (`ensureBridge`): на запуск дома, на явное действие (запуск сценария, «Активный», климат) и когда экрану нужно то, что знает только поток, — `simScenarios()` и `simOptionForms()` (режим «Сценарии», карточка устройства). Открытый и правленный объект без этого потоку не уходит; действия остановленного дома (щелчок, ходьба, двери) не шлются вовсе — движок их всё равно отбрасывает.
- **Скрытое поле событий дома не рисует:** план — только в «Схеме» (`canvasOnScreen`), мини-план и схема в окне — только видимые (`planView.js`); показанное снова перерисовывают смена `screen` и `ResizeObserver`.

## 8. Строки, имена, стили

- **Все видимые строки — в `src/strings.js`.** В разметке только ключи `data-text` / `data-title`. `test/strings.test.js` проверяет словарь в обе стороны: мёртвый ключ и строка без ключа роняют прогон. Латиницу с диакритикой в видимые строки не класть: шрифт ГОСТ рисует её кириллицей (CP1251).
- **Имена:** только именованные экспорты; имена верхнего уровня уникальны во всём `src/`, потому что бандл — одна область видимости. Префикс — по модулю: `volume*`, `sim*`, `scenario*`, `device*`, `hub*`, `blocks*`, `workshop*`, `press*`, `appClock*`. Поэтому поиск символа по имени однозначен.
- **Стили:** все `src/**/*.css` склеиваются текстом. Тест про стили не говорит ничего, кроме сходимости скобок и чисел, повторённых в JS (`test/cssMeasures.test.js`). Правку стилей проверяют глазами.

## 9. Сборка и проверки

`node build.js` (`npm run build`):

1. Читает исходники, строит граф относительных импортов (`dependenciesOf`) и упорядочивает его (`orderModules`).
2. Убирает комментарии, отступы и пустые строки (`stripComments`, у стилей — `stripCssComments`), срезает `import` / `export` (`stripModuleSyntax`) и склеивает модули в один IIFE. Исходники — наполовину комментарии: без них страница 2,8 МБ вместо 7,2 (сжатой по сети 0,67 МБ вместо 1,9). Разбор сверяет `test/buildStrip.test.js`.
3. Собирает второй бандл потока из `src/sim/worker.js` (`workerBundleFrom`), проверяет его чистоту (`assertWorkerPure`) и подставляет строкой (`withWorkerSource`). Вместо `strings.js` в поток идёт выжимка словаря — разделы `WORKER_STRINGS` (`sim`, `rooms.none`) и та же `text`; модуль потока, читающий строку вне выжимки, роняет сборку (`assertWorkerStrings`).
4. Проверяет итог:
   - имена уникальны (`assertUniqueTopLevelNames`; разбор строк и комментариев — `blankLiterals`, он один на сборку и тесты);
   - нет управляющих символов (`assertPlainText`);
   - код и стили внутри страницы (`assertCodeInside`);
   - ссылки только на файлы рядом (`assertLocalLinks`, `assertOffline`);
   - страница и поток разбираются движком JS (`assertParses`).
5. Пишет `dist/`: страницу, шрифт, `sw.js` со списком офлайн-кэша, манифест, значки, `guide.html`.

`npm test` — `node --test "test/**/*.test.js"`: около 3200 тестов за несколько секунд. Два пропускаются без соседнего `../../Sprut.Hub_Tools`.

Тестами закрыты чистые швы:

- модель, файл, таблицы, геометрия;
- кадры `drawScheme` и `volumeDraw` по журналу вызовов `ctx`;
- движок на доме-фикстуре (`test/fixtures/simHome.js`);
- `hubApi` на настоящих сценариях (`test/fixtures/sprut/`);
- бандл Worker, исполненный в Node (`test/buildWorker.test.js`);
- памятка (`test/guidePage.test.js`);
- нормы скорости: медиана после прогрева с запасом ×10.

DOM, вид CSS, IndexedDB и печать не тестируются нарочно. Их проверяет живой прогон: свой сервер, свой Chrome со своим портом, вкладку закрывать, а не перезагружать. Правила — «Живой прогон» в `AGENTS.md`.

## 11. Навигация по коду: ast-index

Индекс собран на весь репозиторий, лежит в кэше `ast-index`, а не в git. Что исключено, задаёт `.ast-index.yaml` в корне: `.claude/`, `graphify-out/`, `tmp/`, `dist/`. Хуки в `.claude/settings.json` обновляют его на старте сессии и после каждой правки файла. Правила поиска — `.claude/rules/ast-index.md`.

```bash
ast-index symbol volumeLampShades           # где объявлено (имена уникальны — ответ один)
ast-index usages canvasCommit               # все места в коде, кроме строк импорта
ast-index callers volumeShadeAlpha          # кто вызывает
ast-index outline scheme_image/src/volume/lamps.js  # все функции и константы файла со строками
ast-index imports scheme_image/src/panels/volume.js
ast-index search LampShade --fuzzy          # по части имени
```

Не символы — значит grep: ключи словаря (`strings.volume.x`, `text("sim.journal." + code)`), поля объекта (`mark.curtainSide`), CSS, слова заказчика в комментариях.

## 13. Две страницы одной сборки (таск 01 просмотра)

Страниц у сервиса две, и обе собраны **одним бандлом**: тот же код, те же
стили, другая разметка.

```
src/index.html  ──┐                       dist/index.html   «Разметка»
                  ├─ buildPage(): один бандл src/**/*.js + один CSS
src/view.html   ──┘                       dist/view.html    «Просмотр объекта»
                                          dist/view.webmanifest (свой start_url)
                                          dist/vendor/**     копия brotli (G18)
```

- **Состав страницы — это её разметка.** Панель монтируется только там, где
  есть её узел (`mountPanel` молча проходит мимо), а в бандл и так попадает
  каждый файл `src/**/*.js`. Второго бандла своего состава нет нарочно: списка
  включения в сборке не существует, и цена его выше веса страницы. Следствие
  честное: страница заказчика весит столько же, сколько «Разметка».
- **Права — один перечень умений.** У сеанса есть род страницы
  (`#app[data-app]` → `app.appKindFor`, `app.appUseKind` при старте), запрет
  выражен белым списком `VIEW_ABILITIES` и одной дверью `appAllows(ability,
  state)` = `layoutAllowsState` ∩ род. Разметки мало: на широком экране правку
  разрешает раскладка. Второго условия в кнопках не заводят.
- **Дом у заказчика идёт сам, в любом режиме.** Правило одно —
  `volumeHomeStarts({simulation, screen, kind, running})`, — и спрашивают его
  **двое**: поверхность «Объёма» и сама панель режима (`mountVolumeScreen`).
  Второе нужно потому, что поверхность собирается по первому входу в режим, а
  режим помнится в браузере (G07): человек, закрывший страницу на «Схеме»,
  возвращался в неё с остановленным домом. Гасит дом только кнопка полосы, и в
  просмотре её нет вовсе (`simBarControls`).
- **Хранилище у просмотра своё** (`store.storeNamespace`): база IndexedDB общая
  на origin, а страницы лежат в одной папке — иначе просмотренные копии
  оказались бы в списке объектов «Разметки», а настройки показа — общими.
- **Служебный скрипт** знает обе страницы по имени и держит каждую под своим
  ключом (D46); в кэш установки идут **обе** (ревью ветки F1): свой запрос
  скрипт не перехватывает — он активируется после загрузки, — а имя кэша
  считается по обеим страницам, и выкладка сносит прежнее имя целиком. Памятка
  в установку не идёт и попадает в кэш при первом открытии.
- **Слова инженера на странице заказчика гасит умение**, а не правка текстов:
  `editHints` (есть в обеих раскладках «Разметки», в `VIEW_ABILITIES` его нет)
  закрывает «правка на компьютере», «загрузите план схемы», «обведите
  комнаты», «задайте высоту в мастерской чертежа», «План не загружен»,
  «этаж задаётся карандашом в строке списка схем», перечень неразмещённых
  меток и запасных габаритов. «Снимок» гаснет `exportFiles`, «Выполнить
  команду» и ряд часов — одной дверью полосы дома (`simBarControls`), отказы на
  клавиши правки — `canvasRefusalText` (`null` — промолчать), зов за
  координатами в строке рассвета — `volumeParamsSunLine`. Плашки
  поля (`createFieldPlate({collapsed})`) на странице просмотра заведены
  сложенными: подсказка — 1 200 знаков про руки, сводка — перепись чертежа.
- **Строки просмотра над полем «Объёма» — третья ячейка угла.** Первые две
  заняты столбиками кнопок (слева знак «?» и «Параметры объёма» — на телефоне
  единственная дверь к часам, погоде и климату; справа полный экран и смена
  вида), а `.view-note` **берёт нажатия**: занятая ими ячейка отнимает и вид, и
  клик. Развёрнутую плашку уводит под строки `--view-notes-h` — их живая
  высота, её ставит `panels/viewStart.js`; нет строк — мера ноль, и поле стоит,
  как стояло (`panels/view.css`).
- **brotli — копия рядом со страницей** (`web/vendor/`, ADR про G18): грузится
  динамическим `import("./vendor/…")` через `src/brotliCodec.js`. Статический
  импорт втянул бы мегабайт в бандл, а `<script src=` в собранной странице
  запрещён. По `file://` кодек не грузится — модуль с чужого источника браузер
  отвергает, и «Ссылкой» отвечает словами.
- **Окно «Сценарии и журнал»** (`panels/viewScenarios.js`) — единственное место сценариев на странице просмотра: читает объект, список берёт у `scenariosListRows`, журнал у `simJournalMount`; «Активный» показан, но не переключается (это шаг истории), ручной запуск — `simScenarioRun`.
- **Плашки поля** (`panels/plate.js`): слева подсказка «?», справа сводка «i», каждая сворачивается и помнит себя порознь; одна на «Схему», «Чертёж» и «Объём».

## 14. Библиотека сценариев (таск 05 просмотра)

Тексты логических и глобальных сценариев лежат рядом со страницей, а не в объекте и не в ссылке.

- **Файлы:** `web/scenarios/<имя>@<16 знаков SHA-256>.js` и `web/scenarios/index.json`; в `dist/scenarios/` попадают сборкой, в git лежат и там и там. Собирает **руками** `node tools/scenario-lib.mjs ~/projects/Sprut.Hub_Tools` (отдельный репозиторий владельца); сборка внешних папок не читает, сети нет. Повторный запуск на тех же исходниках даёт те же байты.
- **Только прирастает:** объект хранит отпечаток, единственная копия текста — файл библиотеки; файл прежнего отпечатка не удалять никогда.
- **Модуль** `scenarioLib.js`: узнаёт точное (байт в байт) совпадение, качает, сверяет отпечаток, кэширует, подставляет `source`. `fetch` и хранилище — аргументами. Строки — `strings.scenarioLib.*`.
- **Порядок:** `scenarioLibResolve(project)` зовётся **до** `buildHomeSpec` (`sim/home.js` берёт уже разрешённые записи); поток имитации сети не имеет и скрипты не грузит. Не нашлось — `simLibraryMissing`, дом стоит без этого сценария.
- **В объекте:** `scenario.lib = {name, version, hash}` вместо `source`, не оба сразу; формат файла 7. Перевод текста на ссылку — `model.migrateScenarioLib` в обеих трубах миграции, затем `panels/projects.js: pinLibraryScripts` (реестр приезжает по сети, поэтому после открытия).
- **Тесты:** `test/scenarioLib*.test.js` (формат, дом, старые объекты).
